# Одновременная работа нескольких пользователей — что менять

Цель: несколько операторов работают параллельно без ощущения «очереди».
Есть два уровня, и оба важны — но **главный тормоз не в Apache/Nginx**.

## TL;DR приоритеты

1. **Демон: пул SSH-сессий на профиль** (изменение в коде) — снимает
   главную сериализацию. **Без этого пункта веб-тюнинг почти не поможет.**
2. **PHP-FPM + mpm_event** вместо Apache mod_php+prefork — параллелизм на
   веб-слое (лёгкие воркеры). Конфиги: `deploy/php-fpm-sed.conf`,
   `deploy/apache-sed.conf`, `deploy/nginx-sed.conf`.
3. **Таймауты прокси** под длинные запросы (до ~10 мин) — уже в конфигах.
4. Кэш демона (20 с / 1 ч для справочников) и асинхронные джобы
   (`submit`/`poll`) уже есть — их менять не нужно.

## Почему главный тормоз — демон, а не веб-сервер

`scripts/pam_daemon.py`: демон многопоточный (поток на соединение), НО у
каждого профиля (СЭД / CHED / KSP) **одна** SSH-сессия `Session`, а
`Session.run()` оборачивает выполнение в `self._lock`:

```python
def run(self, sql, mode, limit, ...):
    with self._lock:          # ← все запросы профиля идут по очереди
        return self._exec(...)
```

Значит запрос пользователя B ждёт, пока по тому же SSH-каналу отработает
запрос пользователя A. Сколько бы воркеров ни было в Apache/Nginx —
на СЭД-профиле всё сходится в одну сессию. Кэш и дедупликация одинаковых
запросов это смягчают, но параллельные *разные* запросы всё равно в очереди.

## Фикс №1 — пул SSH-сессий на профиль (рекомендуемое изменение)

Идея: вместо одной `Session` на профиль держать пул из N (например, 4).
Запрос берёт свободную сессию, выполняет, возвращает в пул. До N разных
запросов профиля идут параллельно.

Эскиз (в `Daemon`):
- заменить `self.sess` / `self.ched_sess` / `self.ksp_sess` на
  `self._pools = {profile: SessionPool(size=N)}`;
- `SessionPool`: список `Session` + `queue.Queue`/`threading.Semaphore`
  свободных; `acquire()`/`release()`; ленивое подключение и переподключение
  «мёртвых» сессий (как сейчас в `_get_session`);
- `_execute_query`: `sess = pool.acquire(); try: sess.run(...) finally: pool.release(sess)`;
- keepalive-поток пингует все сессии пула;
- размер пула вынести в `.env` (`SED_POOL_SIZE=4`, `CHED_POOL_SIZE`, …).

Ограничения, которые надо учесть: PAM-бастион и целевая ВМ должны допускать
N одновременных SSH-сессий (проверить лимиты sshd `MaxSessions`/`MaxStartups`
и политику PAM); PostgreSQL — N доп. коннектов (обычно не проблема).

> Это заметное изменение в конкурентном коде. Его нельзя интеграционно
> прогнать в песочнице (нет SSH/PAM/БД), поэтому делать отдельной задачей
> с юнит-тестами на пул (моками Session) и обкаткой на тестовом стенде.
> Готов реализовать по запросу.

## Фикс №2 — веб-слой (конфиги в deploy/)

- **PHP-FPM** (`deploy/php-fpm-sed.conf`): `pm=dynamic`, `pm.max_children`
  под RAM (≈50 МБ/воркер), `request_terminate_timeout=700s`.
- **Apache mpm_event + proxy_fcgi** (`deploy/apache-sed.conf`) вместо
  mod_php+prefork; `Timeout 700`.
- **Nginx** (`deploy/nginx-sed.conf`): `worker_processes auto`,
  `worker_connections 2048`, `fastcgi_read_timeout 700s`,
  `client_max_body_size 3m`, кэш статики, `include nginx-security.conf`.
- Длинные запросы уже можно уводить в фон через `submit`/`poll` — тогда
  веб-воркер не занят на всё время запроса (poll отвечает быстро).

## Что НЕ трогать (уже сделано правильно)

- `index.php` вызывает `session_write_close()` рано для не-Auth роутов —
  файловая блокировка PHP-сессии не сериализует запросы одного пользователя.
- Кэш демона и дедупликация «в полёте» (`_inflight`) уже снижают нагрузку.
- Лимит тела запроса (2 МБ) и таймауты PHP согласованы с конфигами.

## Проверка после изменений

- Веб-слой: `ab`/`hey` по лёгкому эндпоинту (например `?m=Auth&a=users` на
  стенде) — рост RPS при параллельных клиентах, отсутствие 502/504.
- Демон (после фикса №1): N одновременных «тяжёлых» SELECT на одном профиле
  идут параллельно (время ≈ max, а не сумма); в логе демона
  (`/tmp/sed_daemon.log`) видно параллельные `OK rows=…`.
- Таймауты: запрос длиннее минуты не рвётся прокси (нет 504).
